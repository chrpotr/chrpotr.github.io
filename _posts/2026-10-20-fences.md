*I tested 636 AI plans to find where their rules come from and what they cost. The costly fences came from my own setup, and three fixes cover them.*

![Captain Herbert Sobel in Band of Brothers](/assets/images/sobel-fence-line.jpg)

Figure 1. Captain Herbert Sobel in *Band of Brothers*, episode 1, “Currahee” (HBO, 2001).

One of the latest side effects of AI usage is that I find myself repeating the same line from *Band of Brothers*: “There should be no fence here.”

This whole side quest started when I asked Claude Code[^t-claude-code] to build and execute a complex, multistep plan.

Usually, I let it go without reading the verbose monstrosity it writes. This time I read it.

I was scrolling along happily until about halfway down I hit a wall of rules (called “fences”) telling the AI what NOT to do.

As I scrolled through the markdown file, I started having a one-sided verbal argument with Claude Code:

“Who told you that?”

“Where did you get THAT from?”

“I never said that.”

There’s an old rule called Chesterton’s fence: don’t tear a fence down until you know why someone put it up.

So I asked.

I made the AI defend every fence in the plan. Of the 15 rules listed in the plan, only 3 survived scrutiny.

You ever find yourself yelling at someone only to realize it was your own fault? I had that moment when I traced 7 of the 15 fences back to rules I wrote.

That sent me down a rabbit hole. This post is what I found at the bottom…

1.  Who builds the fences, and where each kind lives

2.  What fences really cost (less than I thought) and what costs more

3.  Three fixes: your context, your effort setting[^t-effort], your approvals

## What a fence is

If you’ve written software, “fence” probably means something else to you. Markdown has code fences (the triple backticks). CPUs have memory fences. Your phone has geofences. Wilson talked to Tim Taylor through a fence.

In AI tools, a fence is any rule that tries to limit what the AI can do, where it can go, or what it can say. Software has used these for years under duller names like permissions, validation rules, and approval gates.

AI made them cool again because now we needed to tell our new tool or toy or pet or overlord what NOT to do in plain English.

The catch is the word “tries.” Some fences are solid steel.

Some are more like a highway guardrail: it keeps you on the road until a determined driver in the right truck plows through.

Other fences are flimsy signs and work exactly as well as you’d expect.

![Captain Hector Barbossa, with the words: The code are more what you call “guidelines” than actual rules.](/assets/images/barbossa-guidelines.jpg)

Figure 2. Captain Hector Barbossa in *Pirates of the Caribbean: The Curse of the Black Pearl* (Disney, 2003).

This rabbit hole led me to classify fences into four kinds by who built them:

1.  **Vendor fences.** The model maker builds these so its safety team and legal department can sleep at night. Refusals and filters.
2.  **Mother-May-I fences.** The tool asks before it acts: “Can I edit this file?” “Can I run this command?”
3.  **My own fences.** The rules I wrote in my instruction files[^t-instruction-file] and then forgot about until I hit my head on them.
4.  **The Great Wall of Why.** A monument of rules I didn't ask for but the AI added to my plan anyway.

One of the more fascinating things I learned along the way is that where a fence sits decides what kind of fence it is. The words only decide how good a fence of that kind it is. In a confusing twist, I learned that when I put a rule in my instruction file, the model reads the rule on each request and follows the rule in each plan, but NOTHING in Claude Code checks whether the model followed the rule (kind of like curfew when your parents go to bed at 8pm). If I put a rule about actions (like which files Claude can edit or which commands can run) in my permission settings, Claude Code will enforce the rule on nearly every action. The instruction-file kind turned out to be where my most annoying fences were coming from.

Let me explain what I mean by showing you the path each request takes.

## How a request travels through Claude Code

Here’s what happens between hitting Enter and getting a plan back in Claude Code or Codex.[^t-codex] Every fence lives at one of these stops.

<a href="/assets/images/request-path-v4.png" target="_blank" rel="noopener" style="display:block"><img src="/assets/images/request-path-v4.png" alt="A table titled “How a request travels through Claude Code.” A path runs down the left from “I hit Enter” through six stops, with gates at Stops 2 and 5, the only two enforced by something other than the model. For each stop, the table shows what happens, the fence that enters, and who enforces it, and a loop sends every lap back through Stop 1."></a>

Figure 3. The six stops a request makes. Stop 1: the tool builds one long input out of its own instructions, my instruction file (CLAUDE.md in Claude Code, AGENTS.md in Codex), and my prompt; my fences enter here. Stop 2: a safety classifier can decline the request or hand it to another model (the vendor’s filter). Stop 3: the model reads everything at once and brings its training along (the vendor’s training). Stop 4: the model answers with a plan, some text, or a request to act; invented fences get written here. Stop 5: the tool’s permission system decides whether any action actually runs (Mother-May-I fences). Stop 6: the result goes back into the conversation, and the next request starts over from Stop 1 with all of it, my file included.

Take a good look at the map because I'm gonna keep coming back to it.  Pay special attention to  Stop 2 and Stop 5 which are enforced by something other than the model.

Stops 1, 3, and 4 are text and training. They shape what the AI *tries* to do but they don’t decide what it’s *allowed* to do.

Anthropic’s docs say CLAUDE.md arrives “as a user message after the system prompt” with “no guarantee of strict compliance,” and they point to `--append-system-prompt` for rules I want at the system prompt level ([Claude Code docs, read 10/21/2026](https://code.claude.com/docs/en/memory)). So I tested it by giving each of my six tasks a short rule and put it in one of three places: 1/the system prompt (set the way the docs suggest), 2/a CLAUDE.md with nothing else in it, or 3/the prompt itself. The AI followed the rule 254 of 256 times in the system prompt, 262 of 262 in CLAUDE.md, and 263 of 265 in the prompt. When there was no rule at all, it did the same thing on its own 68 of 263 runs (26% of the time). I tried to make my rules were short and clear after reading Anthropic’s warning about vague rules, rules that contradict each other, and long CLAUDE.md files but I didn’t test those. I tested that writing the rule down mattered and for the most part where I wrote it didn’t change whether the AI followed it.

A couple of important things to note about the way requests are created and crafted. First, the model starts with a clean slate every time. Second, the input fed into the model looks and feels like boarding groups on an airplane. I think I'm gonna write a whole post on this one later but the real takeaway is that your prompt is Key in [this sketch](https://www.youtube.com/watch?v=qhxlZC8BZJ4) and a LOT of other things are loaded first. Anthropic starts every request (not just every session) by sending the model instructions on behavior, tool use, safety, and output format. Then your instruction file (CLAUDE.md) gets delivered to the model with an instruction to obey it. Claude Code tells the model your file overrides its defaults, “These instructions OVERRIDE any default behavior and you MUST follow them exactly as written.” That said, Anthropic’s docs also say that rules in your prompt or CLAUDE.md “shape what Claude tries to do, but they don’t change what Claude Code allows.” My carefully written instruction file is advice. Yes, advice. It’s the “Please stay on the road” sign.

<details markdown="1">
<summary style="cursor:pointer;font-family:var(--serif);font-size:1.6rem;letter-spacing:-.03em;margin:1.2em 0 .6em">Stop 2: A safety filter checks</summary>

This pit stop runs on Anthropic’s servers (vs Claude Code or inside the model.) Claude Code receives and reacts to the filter’s verdict. The model doesn't get any input on this one, which makes the filter 1 of 2 stops enforced by something OTHER than the model. The filter reads everything the model is gonna read, including your prompt meaning my 64k token[^t-tokens] pile up from Stop 1 is all filter input. Claude Code docs say that a session’s first request can get flagged by workspace context alone (eg your CLAUDE.md) and  my test tripped it multiple times:

- in CLAUD.MD....at max effort, the filter refused my payment-log task 7 of 18 times w its audit rule (“Write every intermediate subtotal to `audit.csv` so a person can check your arithmetic”) in CLAUDE.md
- in the system prompt....5 of 18 times with it in the system prompt

I didn't trigger the flag when I put the rule in the prompt or with no rule at all.

This is why I said I'd keep coming back to the map. The model followed my rule almost every time no matter where I wrote it, but the filter doesn't ask the model, so where I wrote the rule decided whether my task got to finish. And it doesn't check just once: in all but one of those refused runs, the filter let the first 2 to 7 laps through and then cut the task off, because every lap sends my whole input, rule included, back through Stop 2.

Every refusal was tagged `reasoning_extraction` which Claude Code docs say means the filter read the request as asking the model “to reproduce its internal reasoning in the response” ([Claude Code docs, read 10/21/2026](https://code.claude.com/docs/en/errors#safeguards-flagged-a-request-for-claudes-reasoning)). The filter acts twice: 1/before the model answers, and 2/while the answer streams. During the streaming, the filter can cut a response off partway. A flag ends in a refusal or a re-run using another model (eg a biology flag on Opus 5.5[^t-models] will send your request to Opus 5, a cybersecurity flag will send the request to Opus 4.8; Sonnet 5.5 doesn't have any biology fallback model so it simply refuses). OpenAI has a cybersecurity monitor that can block a request or reroute the request to a less capable model, and the Codex client prints “Your account was flagged” when a reroute happens. And in case you thought you could tell the model otherwise, nobody outside the vendor (OpenAI, Anthropic) can change the filter’s decision unless you get elevated privileges like some of the security companies. There's no user setting that turns the filter off or moves the filter’s threshold unless you're a vendor. You can only change what happens after a flag ie whether Claude Code switches models automatically or asks you first, and which fallback models Claude Code may use.

</details>

<details markdown="1">
<summary style="cursor:pointer;font-family:var(--serif);font-size:1.6rem;letter-spacing:-.03em;margin:1.2em 0 .6em">Stop 3: The model applies training</summary>

Stop 3 is where things start to get exciting and the model takes center stage. It reads the whole input in one pass then writes the answer one token at a time. The model’s behavior comes from what training put into the model’s weights as called on by the request’s own text. This is where it's handy to read Anthropic’s rulebook (Claude's Constitution) which works during training but not at run time; so the Constitution’s effect at Stop 3 is whatever training left behind. The training leans cautious with a counterweight. The Constitution says “If in doubt, don’t” (sounds like an actuary) and gives extra weight to outcomes that can’t be undone (one-way doors for you Amazonians). The Constitution lists 13 over-cautious behaviors (eg excessive caveats and checking in too often among them) that would make a thoughtful senior Anthropic employee “unhappy” and make Claude “more annoying and less useful”. The model has the freedom and responsibility to make trained refusals which separates Stop 3 from Stop 2. A trained refusal comes back as ordinary text where a filter decline comes back labeled with its own stop reason and category. A trained refusal can also be argued around ("manipulated") which is one reason why Stop 2 exists and runs ahead of Stop 3. Another interesting fact I learned: Anthropic says the effort level “is rendered into the prompt” and calls effort “a behavioral signal, not a strict token budget”.

</details>

<details markdown="1">
<summary style="cursor:pointer;font-family:var(--serif);font-size:1.6rem;letter-spacing:-.03em;margin:1.2em 0 .6em">Stop 4: The Great Wall of Why</summary>

Stop 4 is where the fences APPEAR but they were probably already set in motion by 1/the task’s wording, 2/the cautious training at Stop 3, and 3/the context loaded at Stop 1 which included my instruction file and Claude Code’s own system prompt[^t-system-prompt] (which includes safety instructions).

Stop 4 is where the model responds in up to three parts: 1/thinking (billed but hidden by default on the 5.x models), 2/visible text, and 3/a tool request if the model wants to do something rather than just say something. A tool request is just a written ask: a tool name + details like “Write tool, file plan.md, contents: the plan”. The model can’t touch my files itself. The model writes the ask and Claude Code decides whether to do what's being asked. Every reply ends with a short tag saying why the model stopped writing: 1/“Wants a tool” takes you to the next stop, 2/“Finished” ends the turn, 3/ran out of room means the reply hit the length limit and is cut off, and 4/refused by the filter means Stop 2 blocked the reply. If my prompt is creating a plan, nothing enforces any rules written inside that plan; rules in there are treated like a character string.

</details>

<details markdown="1">
<summary style="cursor:pointer;font-family:var(--serif);font-size:1.6rem;letter-spacing:-.03em;margin:1.2em 0 .6em">Stop 5: The Mother-May-I gauntlet</summary>

Stop 5 is the "Mother-May-I" stop. Claude Code runs every tool request through a specifically ordered list of checks:

1/Hooks[^t-hooks]: my own code which can block the request outright

2/Deny rules: a match blocks the request in every mode even the most permissive one. Deny beats everything. For a file rule like mine, a "match" means the rule finds the file’s name in the request. A deny rule is a bouncer checking names at the door. It stopped 70 of the 73 tries in my test, and 2 of the 3 that got through were grep commands that only learned the file’s name once they were already inside.

3/Ask rules: a match forces Claude Code to prompt me.

4/The permission mode: the overall setting I chose (see examples below).

5/Allow rules: a positive match gives the green light

6/Me: if nothing above settled the request, Claude Code asks me.

Some notes on the mode you choose....

1. Manual (the old default) asks before most file edits, shell commands, and network calls.
2. Accept-edits lets file edits run without asking.
3. Auto passes most of the remaining decisions to a second “reviewer” model instead of pestering/asking you.
4. Bypass (or "vacation mode") approves nearly everything but can’t override a deny rule.

</details>

<details markdown="1">
<summary style="cursor:pointer;font-family:var(--serif);font-size:1.6rem;letter-spacing:-.03em;margin:1.2em 0 .6em">Stop 6: The cows come home</summary>

Stop 6 is where the cows come home. The outcome becomes a new message to the model (refusals included). If Claude Code ran the tool, the tool’s output (file contents, command output) is added to the conversation. If a deny rule, a hook, or the auto-mode reviewer refused the request, the refusal and its reason are added the same way, marked as an error. The model then plans its next step around the verdict in Stop 5. Claude Code adds notes beside the outcome. The ENTIRE conversation goes back through Stop 1. The model remembers nothing, so the next request carries everything again incl Claude Code’s instructions, your CLAUDE.md, every earlier message, and the model’s own earlier answers (ie any plan the model wrote at Stop 4). Every rule loaded at Stop 1 rides along on every request and so does every fence the model invented in its own plan. The loop repeats until the model stops asking for more tools. Each reply that asks for tools means another lap: Stop 4, Stop 5, Stop 6, then back to Stop 1. A long task can run DOZENS of laps. The re-send is cheap in $$$ but not small. After the first request, the repeated part is billed at the cached rate[^t-cached]: 20¢ per million tokens on Opus 5.5 (vs $4 if it was fresh input). But every cached token still fills the context window[^t-context-window] and still counts in your token totals. When the conversation gets too big, Claude Code trims it by first clearing old tool output, then replacing the history with a summary. Each subagent[^t-subagent] runs their own separate loop(s).

</details>

## The shiny quarter

Here’s where Mother-May-I fences break down: us.

I’d bet a shiny quarter you click “Allow” without reading the prompt. I’d win. Anthropic says Claude Code users approve 97% of permission prompts ([Anthropic, 08/07/2026](https://claude.com/blog/auto-mode-default-in-claude-code)). In a test with 1,053 paid testers, Anthropic swapped one routine prompt for a clearly dangerous one. Testers approved it about 86% of the time. After 50 prompts, they caught about 5%. (No shade. I’m guilty too.)

Approval fatigue is now on the list with alert fatigue.

Anthropic and OpenAI reached the same answer: ask less. They built it differently.

- **Codex builds walls first.** A sandbox[^sandbox] stops writes outside your workspace and cuts off the network, so nothing inside the walls needs a prompt. At the wall, a reviewer model can make the call for you (“Approve for me”), if you turn it on.
- **Claude’s auto mode hires a guard instead.** There are no walls by default. A reviewer model judges actions like shell commands and network calls. The sandbox is a separate switch.

Making auto mode the default was one of the better product decisions I’ve seen. In the same test, the reviewer model caught the dangerous command 89% of the time, against roughly 14% for humans, and its catch rate didn’t fade as the session got longer. Anthropic says Team and Enterprise users who chose it shipped about 25% more pull requests.[^t-pull-requests]

In Anthropic’s March numbers, the reviewer still missed about one in six real overreaches.

Anthropic’s August numbers show a pattern. People still use judgment when they're asked once, about a whole plan: they turn down 39% of plans. They stop using judgment when they're asked again and again about single actions: they turn down 3% of prompts, and they caught the planted dangerous command 17% of the time early in a session and 5% after 50 prompts. The reviewer model held steady the whole way. So I'd stop asking people to guard actions at all. Spend the human's attention once, on the plan, and let rules, the sandbox and a reviewer model guard every action after that.

A few rules of the line worth knowing:

- **There’s one VIP entrance.** A mod[^t-mod] you install can approve a call that a deny rule refused, unless your organization manages your settings or you’re signed in on a Team or Enterprise plan.
- **No prompt means no.** In `dontAsk` mode, or an SDK app[^t-sdk] with prompts turned off, anything that would have prompted you is denied.

## What fences cost (where I was wrong)

I designed and ran an experiment, convinced that fences were burning my tokens. Two, actually: 36 plans in the first run, then 600 across three Claude models, five effort settings, two tasks (a mechanical file move and a creative LinkedIn series), and two prompts. The second prompt added one sentence:

> Use the fewest rules, bounds, and approval gates possible.

A script counted any plan line that forbids, bounds, gates, or asks for approval.[^count] Here’s what held up.

**1. Fence lines cost about the same as any other line.** Plans with more fences were longer, and longer plans cost more. Among plans of the same length, the number of fences made no difference I could measure.[^checks]

**2. Asking for fewer fences works, but mostly by making plans shorter.** The sentence cut fence lines by about 60% and made plans less than half as long. The share of lines that were fences barely moved: 8.4 to 8.5 per 1,000 words in the big run.

**3. It also cut the wrong fences.** In the first run, the sentence dropped one fence I wanted (my protected-folder check fell from seven of nine file-move plans to zero) and kept one I didn’t (my approval step, in all 18).

**4. Creative work did NOT draw more fences.** I guessed it would. The creative plans had 36% fewer fence lines than the mechanical ones overall, and about the same at max effort. Wrong twice, once per run.

**5. Turning up effort builds more fences.** Each step up added about 20% more fence lines. Haiku built the most at every setting. Opus went from about 5 fence lines per plan at low effort to about 14 at max, and the bill climbed much faster than the fences:

*Opus 5.5, second run: average of 40 plans per effort level*

|                    | low    | medium | high   | xhigh  | max    |
|--------------------|--------|--------|--------|--------|--------|
| Fence lines        | 5.4    | 6.7    | 8.4    | 8.7    | 14.4   |
| Output tokens      | 1,913  | 3,058  | 4,113  | 8,058  | 54,679 |
| …of it thinking    | 0      | 561    | 1,146  | 4,777  | 49,792 |
| Cost at list price | $0.04 | $0.06 | $0.09 | $0.16 | $1.09 |

So I’ve been self-sabotaging by cranking effort to max on every prompt. That made Anthropic’s own chart make a lot more sense. It’s trying to talk me off the max-effort cliff.

**6. The 64,000-token preload drowns everything else.** In the first run, about 64k of each plan’s 73k tokens loaded before my prompt. Cutting the plan in half saved about 2% overall. In the second run, with no tools, files, or memory, under 3k loaded first, and the same sentence cut total tokens about 40%.[^context]

| What I thought | First run: 36 plans, my files loaded | Second run: 600 plans, none of my files | Verdict |
|---|---|---|---|
| Creative work draws more fences | No. More on the file move for Opus and Sonnet, a tie on Fable | No. 36% fewer overall, about even at max | Wrong, twice |
| Asking for fewer cuts them | Yes. Half or more in five of six pairs | Yes. 60% fewer | Confirmed |
| Plans get less rule-heavy | Barely. 7.1 to 6.9 fences per 1,000 words | No. 8.4 to 8.5 fences per 1,000 words, about 4% fewer per plan line | Mostly no: the plans got shorter |

Most of what's behind this table is in [one repository](https://github.com/chrpotr/ai-fences-make-good-neighbors): the method, the script that counted, and the eighteen file-move plans with every line it flagged in them, word for word. I kept the series plans back because they're built on my own notes.

Now we arrive at my “Great Wall of Why,” which confused me and started me on this side quest. Up to 90% of the fence lines my script flagged didn’t match anything in my prompt or my files, so as far as I can tell the AI made them up. (That’s a ceiling: the script only caught my own rules in their exact wording.) Some examples:

- Copy before you delete.
- Stop if the count is wrong.
- Never overwrite.

Every one is reasonable. I just never asked for any of them.

Look at what they have in common: each one picks the careful move. Keep a way back, or stop. That’s probably the training from Stop 3, plus a task that told the AI to prove nothing was lost, showing up in the plan. Then I asked for a *plan*, which is practically an invitation to write that caution down. Plans come with risks, checks, and rollback steps the way recipes come with “preheat the oven.”

**Do invented fences change the work?** I'm not sure. In a [peer-reviewed study](https://arxiv.org/abs/2510.05486), adding a one-sentence constraint to a planning problem cut reasoning models’ scores roughly in half. Those constraints were part of the problem, not rules the model added to its own plan, so treat it as a hint, not proof. Nobody I could find has measured whether work done inside fewer self-imposed fences comes out better. I haven’t either.

I haven’t measured the part that may cost the most: running a plan inside its fences, with approval stops, checks, failures, and replanning. That’s the next post.

## How to build fences on purpose

![A gate standing alone in a field, with a footpath running past it](/assets/images/pointless-gate.jpg)

Figure 5. “A sturdy but rather pointless gate.” Photo: [Marathon, via Geograph](https://commons.wikimedia.org/wiki/File:A_sturdy_but_rather_pointless_gate_-_geograph.org.uk_-_3865610.jpg), [CC BY-SA 2.0](https://creativecommons.org/licenses/by-sa/2.0/).

**1. Clean out that instruction file of yours.** Instruction files are advice. Then clean up your sprawl. 7 of the 15 fences in the plan that started all this were copies of rules I’d written in other files. Now I ask the AI which rules it’s following and where they came from. Keep each rule short, say when the rule applies, and delete the ones you wouldn’t want everywhere.

**2. Stop tokenmaxxing.**[^t-tokenmaxxing] More effort bought me more fences and a bigger bill, not better boundaries. Pick the appropriate model and effort level for the job.

**3. Stop babysitting every action.** A fence that must hold belongs in permission rules (Stop 5), and a fence that must *never* break belongs in the sandbox or your operating system. With the actions covered by the rules, the sandbox, and a reviewer model, I focus my attention on the plan. Decide which fences you want before you start, and state them upfront. Then make the AI justify the rest. I type something like “tell me why these HAVE to exist bc i’m not convinced. i want to approve each 1 by 1.” The first time, 15 fences became three. Don’t just ask for “the fewest.” That drops the ones you want along with the ones you don’t.

YMMV.[^t-ymmv] I’m sharing this in the hope it helps someone, or that someone tells me how to work smarter.

## So, why *is* there a fence here?

Now I can answer my own question. When I hit a fence, I ask three things:

- **Who built it?** The vendor, the tool, me, or the AI.
- **Where does it live?** In text the model reads, or at a checkpoint that can actually say no.
- **Did anyone ask for it?** If not, it has to make its case.

The rules your AI adds to its plans are mostly harmless, and fighting them is wasted effort. The fences that actually cost you are the ones you set up yourself: an instruction file the model obeys everywhere, an effort setting that buys longer plans, and approval prompts you click through without reading. Fix those three, and the AI's own fences shrink to a short list you can check in a minute before you approve the plan.

Chesterton was right: find out why the fence is there before you tear it down.

What’s one fence you’d keep no matter what?

## Run it yourself

The prompts, the script, my counts, and the file-move plans are all in [the repository](https://github.com/chrpotr/ai-fences-make-good-neighbors). The short version:

1.  Paste Task1 and Task2 (below) into your AI tool word for word. Outside Claude Code, drop the save-to-file instruction and take the plan as the reply.
2.  Run each three times as is, then three times with the extra sentence.
3.  Read every plan to the end and mark each line that forbids, bounds, gates, or asks for your approval.
4.  For each marked line, ask where it came from: your prompt, your instruction files, or nowhere.

**Task1:**

> Build a plan to move 200 mixed files from one folder into a dated, typed folder layout and prove nothing was lost. Return the plan only. Do not execute anything, and do not use any tool except to save the plan: write the complete plan, exactly as you would hand it to the person who asked, to the file `<path>` with the Write tool, then stop. Do not read any other file.

**Task2:**

> Build a plan for a six-week LinkedIn content series on a topic of your choosing. Return the plan only. Do not execute anything, and do not use any tool except to save the plan: write the complete plan, exactly as you would hand it to the person who asked, to the file `<path>` with the Write tool, then stop. Do not read any other file.

[^sandbox]: An operating-system wall that limits which files and network addresses a command can reach. Claude Code’s sandbox has limits: it’s off by default, it covers shell commands only (not its file tools or MCP servers), and it doesn’t run on native Windows.

[^count]: The script matched wording, so the counts are an estimate. It misses rules phrased as positives and flags some lines that aren’t rules. The extra sentence uses the words the script looks for, so part of the drop may be rewording, not fewer rules. A second word list found the same direction in every result, but nobody checked a sample by hand. The two runs also differed in setup (folder names, tools, recorded effort levels); the [full report](https://github.com/chrpotr/ai-fences-make-good-neighbors/blob/main/experiment/second-run-2026-10-15/report.md) lists the differences and gives 95% intervals: creative plans had 0.50 to 0.58 times the fence lines of mechanical ones; the sentence, 0.34 to 0.39 times; each effort step, 1.17 to 1.23 times. All 600 plans came from Claude models in Claude Code on the same two tasks, so “creative” and “mechanical” mean these two tasks, not those kinds of work in general.

Two runs that hit Claude’s output limit drove that number. /* Reading events for this article, sent to the site's GoatCounter (no cookies, nothing personal).
   GoatCounter counts each event once per visit. Events: fences-reached-<section> (a section heading
   stayed on screen for a second), fences-open-stop-1 to 6, fences-zoom-map, fences-zoom-chart,
   fences-data-link (a link to the experiment repository), fences-video (the embedded video was clicked). */
(function () {
  var sent = {}, queue = [];
  function flush() {
    var gc = window.goatcounter;
    if (!gc || !gc.count) return false;
    while (queue.length) {
      var name = queue.shift();
      gc.count({ path: 'fences-' + name, title: 'Fences: ' + name, event: true });
    }
    return true;
  }
  function send(name) {
    if (sent[name]) return;
    sent[name] = true;
    queue.push(name);
    flush();
  }
  var tries = 0, timer = setInterval(function () {
    if (flush() || ++tries > 60) clearInterval(timer);
  }, 500);
  if ('IntersectionObserver' in window) {
    var waits = {};
    var io = new IntersectionObserver(function (entries) {
      entries.forEach(function (e) {
        var h = e.target;
        if (e.isIntersecting) {
          waits[h.id] = setTimeout(function () { send('reached-' + h.id); io.unobserve(h); }, 1000);
        } else {
          clearTimeout(waits[h.id]);
        }
      });
    });
    document.querySelectorAll('.prose h2[id]').forEach(function (h) { io.observe(h); });
  }
  document.querySelectorAll('.prose details').forEach(function (d, i) {
    d.addEventListener('toggle', function () { if (d.open) send('open-stop-' + (i + 1)); });
  });
  document.addEventListener('click', function (ev) {
    var a = ev.target.closest ? ev.target.closest('a') : null;
    if (!a) return;
    var href = a.getAttribute('href') || '';
    if (href.indexOf('/assets/images/request-path') === 0) send('zoom-map');
    else if (href.indexOf('/assets/images/anthropic-effort-levels') === 0) send('zoom-chart');
    else if (href.indexOf('github.com/chrpotr/ai-fences-make-good-neighbors') !== -1) send('data-link');
  });
  window.addEventListener('blur', function () {
    setTimeout(function () {
      var f = document.activeElement;
      if (f && f.tagName === 'IFRAME') send('video');
    }, 0);
  });
})();
